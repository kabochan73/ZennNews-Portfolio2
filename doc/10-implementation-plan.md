# 実装計画

[← 目次に戻る](README.md)

## 進め方

| 項目 | 方針 |
|---|---|
| 実装担当 | Claude が実装し、開発者（本人）がレビューする |
| 書く前の説明 | コードを書く前に、何を書くか（ファイル・内容・理由）を軽く説明し、了承を得てから書く |
| コミット前の確認 | コミットする前に、開発者がコードを確認する。OK をもらってからコミットする |
| 説明 | 各フェーズの終わりに、何をなぜそう書いたかを説明する（面接で説明できるように） |
| ペース | 1フェーズずつ進める。フェーズが終わるたびに確認をもらってから、次のフェーズに進む |
| コミットの粒度 | 1コミットあたり、変更ファイルは5つ程度を目安にする |
| コミットの例外 | フレームワークの初期化（`composer create-project` / `create-next-app`）のように、ツールが一度に大量のファイルを生成するものは、生成物をまとめて1コミットにする |
| ブランチ | `main` に直接コミット・push する |
| 品質 | 各フェーズの終わりに、テストと Lint が通った状態にする |

## フェーズ

| フェーズ | 内容 | 完了の目安 |
|---|---|---|
| 0. 土台づくり ✅ | Git・GitHub リポジトリ、docker compose（db / backend / frontend）、Laravel と Next.js の初期化、Lint・フォーマッタの設定 | `docker compose up` で両方の初期画面が表示される |
| 1. DB ✅ | マイグレーション（7テーブル）、モデル、タグの Seeder（42タグ） | `migrate --seed` が通る |
| 2. 記事の取得 ✅ | 取得コマンド、100件を超えた分の削除 ＋ Pest | ローカルでコマンドを実行すると記事が保存される |
| 3. 認証 API ✅ | 新規登録、ログイン、ログアウト、`/me`、退会 ＋ Pest | API 1〜5 のテストが通る |
| 4. 機能 API ✅ | タグ、記事一覧、ブックマーク、既読 ＋ Pest | API 6〜13 のテストが通る |
| 5. フロントの基盤 ✅ | 最初に ISR に合わせたバックエンドの変更（記事一覧・全タグの API をログイン不要に、`GET /api/me/home` の追加、`GET /api/bookmarks` の削除、取得後の通知）。その後、Vitest の準備、Laravel の呼び出し（`lib/laravel.ts`）、Route Handler（ログイン・新規登録・中継・`/api/revalidate`）と Cookie、`proxy.ts`、TanStack Query、トースト、ヘッダー、下のタブ、フッター | 仕組みと共通の部品がそろい、ログイン → 中継 → Laravel、Laravel → `/api/revalidate` の流れを実際に動かして確かめられる（画面での確認はフェーズ6） |
| 6. 画面 | トップ → 新規登録・ログイン → タグ設定 → ホーム → エラー画面 ＋ Vitest | 新規登録・ログインして `/home` が開け、すべての画面が動く |
| 7. E2E と CI | Playwright、GitHub Actions（Lint・Pest・Vitest・Playwright） | CI がすべて通る |
| 8. デプロイと仕上げ | 本番用 Dockerfile、Railway（frontend / backend / cron / PostgreSQL 17）、環境変数、Wait for CI、README（ポートフォリオ用の説明） | 本番で一通り使える。push で自動デプロイされる |

## この順番にした理由

- **デプロイは最後にまとめて行う（フェーズ8）**：開発中はローカル（Docker）で完結させる。本番特有の問題（本番用 Dockerfile、Railway の設定、環境変数、サービス間の通信）は最後にまとめて対応する
- **記事の取得を早めに作る（フェーズ2）**：画面を作るときに、本物の記事データを使って確認できる。開発中はローカルでコマンドを手動実行してデータを用意する
- **バックエンドの API を先に固める（フェーズ3・4）**：フロントは完成した API に合わせて作れる

## 注意点

- 本番の記事は、デプロイして Cron が動き始めてから溜まり始める（1日30件ずつなので、100件に近づくまで数日かかる）

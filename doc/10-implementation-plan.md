# 実装計画

[← 目次に戻る](README.md)

## 進め方

| 項目 | 方針 |
|---|---|
| 実装担当 | Claude が実装し、開発者（本人）がレビューする |
| 説明 | 各フェーズの終わりに、何をなぜそう書いたかを説明する（面接で説明できるように） |
| ペース | 1フェーズずつ進める。フェーズが終わるたびに確認をもらってから、次のフェーズに進む |
| コミットの粒度 | 1コミットあたり、変更ファイルは5つ程度を目安にする |
| コミットの例外 | フレームワークの初期化（`composer create-project` / `create-next-app`）のように、ツールが一度に大量のファイルを生成するものは、生成物をまとめて1コミットにする |
| ブランチ | `main` に直接コミット・push する |
| 品質 | 各フェーズの終わりに、テストと Lint が通った状態にする |

## フェーズ

| フェーズ | 内容 | 完了の目安 |
|---|---|---|
| 0. 土台づくり | Git・GitHub リポジトリ、docker compose（db / backend / frontend）、Laravel と Next.js の初期化、Lint・フォーマッタの設定 | `docker compose up` で両方の初期画面が表示される |
| 1. 早めのデプロイ | Railway に最小構成でデプロイ、CI（GitHub Actions）の最小構成 | 本番URLで初期画面が開く。push で自動デプロイされる |
| 2. DB | マイグレーション（7テーブル）、モデル、タグの Seeder（30タグをここで決める） | `migrate --seed` が通る |
| 3. 記事の取得 | 取得コマンド、100件を超えた分の削除、Railway Cron の設定 ＋ Pest | 本番DBに記事が溜まり始める |
| 4. 認証 API | 新規登録、ログイン、ログアウト、`/me`、退会 ＋ Pest | API 1〜5 のテストが通る |
| 5. 機能 API | タグ、記事一覧、ブックマーク、既読 ＋ Pest | API 6〜13 のテストが通る |
| 6. フロントの基盤 | Route Handler での中継と Cookie、TanStack Query、ヘッダー、ハンバーガーメニュー、フッター、トースト | ログインしてからログアウトまでの流れが画面で動く |
| 7. 画面 | トップ → 新規登録・ログイン → タグ選択 → マイフィード → 設定 → エラー画面 ＋ Vitest | すべての画面が動く |
| 8. E2E と仕上げ | Playwright、CI に E2E を追加、README（ポートフォリオ用の説明） | CI がすべて通り、本番で一通り使える |

## この順番にした理由

- **早めにデプロイする（フェーズ1）**：Docker、FrankenPHP、Railway、Cookie での認証まわりは、ローカルでは動いても本番で詰まりやすい。最初に道を通しておく
- **記事の取得を早めに作る（フェーズ3）**：本番で動かし始めれば、画面を作っている間に記事が溜まる（1日30件ずつなので、100件に近づくまで数日かかる）
- **バックエンドの API を先に固める（フェーズ4・5）**：フロントは完成した API に合わせて作れる
